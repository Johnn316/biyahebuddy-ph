# CLAUDE.md — BiyaheBuddy PH

## Project summary

BiyaheBuddy PH is an **offline** AI driving companion Android app for Filipino
drivers, built in Flutter for a hackathon. Features: emergency SOS (GPS + SMS +
dialer + volume-button trigger), fines lookup when flagged (LTO/MMDA/city),
on-device AI Q&A about traffic laws (RAG over local law chunks), number-coding
status, and a driver profile with QR card.

Package: `ph.biyahebuddy.biyahebuddy_ph` · minSdk 26 · state: Riverpod ·
routing: go_router · storage: sqlite3 + shared_preferences.

Pinned on purpose: `permission_handler: ^12.0.1`. The 13.x line pulls
`permission_handler_android` 14.x, and its Gradle script fails to compile with
this project's AGP 8.11 / Kotlin 2.2 setup. Don't bump it without running
`flutter build apk --debug`. Riverpod is on 2.6.x, the newest version this
SDK (Flutter 3.41) can resolve.

## Hackathon rules (must follow)

- Deadline 10:00 AM Oct 10, single submission, code freeze. Repo must be PUBLIC by then.
- Core AI must run ON-DEVICE: local LLM, local speech recognition, local RAG. Cloud only optional/secondary.
- Internet ONLY for one-time model download. Everything else works in airplane mode.
- Keep docs/AI_DISCLOSURE.md updated (every model, package, framework, API, asset, AI dev tool) with sections "Runs locally" and "Requires internet".
- Never commit secrets, .env, or model files.
- Feature freeze 3:00 AM; bug fixes only after.

## Offline-first rule (non-negotiable)

- Every feature must work with **no network**. Never add a runtime network call.
- The only allowed network use is the **one-time on-device model download**.
- No analytics, no cloud APIs, no remote config.
- Speech recognition is local only (`SpeechService`, e.g. Whisper). Never use
  Android's `SpeechRecognizer` or `speech_to_text`; they can fall back to Google's
  online recognizer.
- Model download goes only through `ModelManager.downloadModels()`.
- LLM model files are never committed (`*.gguf *.task *.tflite *.bin *.litertlm models/`
  are git-ignored).

### Data schemas (`assets/data/`)

- `laws.json`: `[{id, source, section, title, text, tags, url, as_of, notes?}]` — generated by `tools/build_data.py`; `notes` only on amended/amending sections
- `fines.json`: `[{violation, agency: lto|mmda|city, amount, legal_basis, aliases}]`
- `hotlines.json`: `[{name, number, zone}]` (`zone: null` = nationwide)
- `coding.json`: `{scheme, hours, days: {"1": [digits], ...}, notes}` (ISO weekday keys)

`laws.json` is built from official texts (see `docs/SOURCES.md`); the other files are still **SAMPLE** data — not verified.

## AI answer-format rules (in-app assistant)

Every `AiAssistant` answer must be, in order, each header on its own line
as `**<Header>**` (the chat UI parses these exact headers; short forms
`Batas` / `Gagawin` are also accepted):

1. **Kalma muna** — short, calming opener (driver may be stressed).
2. **Ano ang sinasabi ng batas** — the relevant law **with citation**
   (e.g. `RA 4136 Sec. 42`, `RA 10913 Sec. 4`, `LTO JAO 2014-01`,
   `MMDA Reg. 96-005`; these are auto-highlighted as chips). Never invent a
   law; if no chunk matches, say so plainly.
3. **Pagsusuri** — analysis of the driver's situation.
4. **Ano ang gagawin** — numbered, concrete next steps.

If no headers are found the UI shows plain text. Stream tokens as they are
generated (`Stream<String>` chunks are appended in order).

Also: Filipino/Taglish by default, short sentences, no legal-advice claims,
cite only from `laws.json` / `fines.json` retrieved chunks, recommend 911 when
anyone is hurt. `analyzeTwoSides` stays neutral between Driver A and Driver B.

## UI rules

- iOS-inspired design (not a copy of any app): iOS system colors, inset
  grouped lists (`GroupedSection` / `GroupedTile`), large titles, Cupertino
  icons/transitions/segmented controls/action sheets, haptics on primary taps,
  very soft shadows (none in dark). `ThemeData.platform = iOS` on purpose.
- Navigation: floating frosted tab bar (Home · Buddy · Na-flag · Profile) via
  `StatefulShellRoute` in `core/router` (`features/shell/main_shell.dart`).
  Emergency, QR, IPAKITA and onboarding are full-screen above the tab bar
  (push on the root navigator). Tab screens must pad their bottom by
  `MediaQuery.paddingOf(context).bottom` (body extends behind the bar).
- Large, high contrast, one-thumb use. Layouts fill their space and must not
  overflow at the largest system font. Tests: `test/screens_matrix_test.dart`
  (every screen × light/dark × 1.0x/2.0x × phones + tablets) and
  `test/home_fit_test.dart` (Home fully visible above the tab bar).
- Tablets: content is centered at max 640dp (`ContentWidth`).
- Theme lives in `lib/core/theme/` (frontend-owned). Bundled Plus Jakarta Sans
  (never runtime-fetched). ThemeMode follows System by default; Profile has
  "Sundin ang system" switch + Light/Dark (`themeModeProvider`, persisted).
- **Never hardcode colors in features/.** Use `context.colors` and
  `context.palette` (`AppPalette`). Exceptions: QR always black on white;
  IPAKITA always uses the dark theme.
- Red (`palette.emergency`, #FF3B30) is ONLY for SOS/emergency — not even
  for validation errors (those are amber). Coding badge + citations = amber
  `palette.accent`; safe/OK = green `palette.success`; links = #0A84FF.
- Reduce motion: the SOS rings stop pulsing; widget tests run with reduce
  motion on (`test/flutter_test_config.dart`).
